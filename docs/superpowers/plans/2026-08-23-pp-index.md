## Cross-plan dependencies

- **PP-0 → PP-1, PP-2, PP-4, PP-6, FT-1.** The shared shell is where those edits land once instead of three times. PP-0's own C# half (Tasks 7-9) is owned by PP-1 if PP-1 is already in flight.
- **PP-2 → PP-3, PP-4.** All three touch the same `chat-ui.ts` region.
- **PP-5 → PP-12 (Task 3), PP-14 (Task 1), PP-15, PP-16, PP-22.** Each says explicitly what to skip if PP-5 already landed.
- **PP-21 → PP-22 (Task 1).** PP-21 corrects `PptChartTypeMap["bar"]`, which maps to xlColumnClustered today; PP-22's enum must be derived from the corrected map.
- **PP-10 (Task 1) → PP-11.** `RangeAfterBlock` is produced by PP-10 and consumed by PP-11; whichever lands first writes it.
- **PP-21 (Task 2 Step 5)** also fixes Excel's identical `legendPos` defect — deliberately not split across two plans.
- **PP-8 (Task 1 Step 4) ↔ PP-19.** The scope note that PP-8 relocates lists `delete_slide` as out of scope; PP-19 Task 1 puts it back in and removes it from that list.

## Conventions every plan follows

- Task-by-task with `- [ ]` steps, `**Files:**` and `**Interfaces:**` blocks, matching `2026-08-22-word-tools-completion.md` and its siblings.
- C# 7.3 / .NET Framework 4.8 only — no `using`-declarations, no target-typed `new()`, no switch expressions.
- No automated tests for COM executor methods (project convention); `shared/chat-ui` changes do get vitest coverage.
- Rebuild the esbuild bundle **and** re-run MSBuild after any `entry.ts` or `chat-ui.ts` change; bundles are gitignored and a stale one silently ships old behavior.
- **The recurring rule across nearly every plan:** never report success for work that did not happen. Where a capability cannot be delivered, the tool says so with an error the model can act on. Most of the P1/P2 items in this set are instances of that one defect.
