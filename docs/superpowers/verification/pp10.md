## What was built

- `RangeAfterBlock(int afterBlockIndex)` — the shared insertion-point resolver, explicit bounds validation (no silent clamping), `-1` = start of document. Consumed by `insert_content`, `edit_chart`'s anchored creation (PP-9), and `add_image` (PP-11).
- `InsertContent` — backward compatible (no position/html → exact original end-of-document behavior); `afterBlockIndex` anchors the insert; multi-line `text` splits into one paragraph per line instead of literal embedded line breaks; reports the 0-based inserted paragraph range.
- `ReplaceBlocks` — captures and reapplies the first replaced paragraph's style by default (`preserveFormatting`, default true); `preserveFormatting: false` restores the old strip-everything behavior; reports what was preserved.
- `InsertHtmlFragment`/`ParseHtmlFragment`/`WriteInlineNodes` — restricted HTML subset (`<p> <h1>-<h3> <ul>/<ol>/<li> <b>/<strong> <i>/<em> <u> <br/>`), parsed via `System.Xml.Linq.XElement.Parse` (well-formedness for free), fully validated against the supported tag set *before* any Word write happens (Task 3 Step 4's requirement). `<br>` is normalized to `<br/>` before parsing. Wired into both `insert_content` and `replace_blocks` as an `html?` alternative to `text` (exactly one of the two required; both present errors).
- `read_blocks` gained `format?: 'text'|'html'` (default `'text'`, unaffected existing behavior). HTML mode walks each paragraph's `Range.Words` tracking bold/italic/underline state to emit the same restricted subset, wraps list-item runs in `<ul>`/`<ol>`, derives heading tags from style name, HTML-escapes text, and is capped at 100 paragraphs per call with a specific error above that.
- System prompt updated to mention positional insert and the HTML subset.

## Real risk areas — read before testing

1. **`InsertHtmlFragment`'s paragraph-writing loop** (`cursor.Paragraphs[1]` after writing inline content) assumes the cursor, after `WriteInlineNodes` finishes, is still positioned within the paragraph just written (not past its paragraph mark) so that `Paragraphs[1]` resolves to that exact paragraph for applying heading style / list format. This is standard Word Range behavior but is genuinely untested here.
2. **`ReadBlockAsHtml`'s per-word formatting-state walk** is a simplification: Word's `Range.Words` splits on word boundaries, and I track bold/italic/underline transitions between consecutive words. It will not perfectly reconstruct formatting that changes *mid-word* (rare, but Word does allow it) — documented as an acceptable simplification given this file's "no automated tests for COM code" convention and the plan's own note that some fidelity loss outside the exact subset is expected. Format-preservation loss is limited to that edge case; headings, whole-word bold/italic/underline, and list membership should round-trip correctly.
3. **Performance of `format:'html'`** was not measured against a real 50-page document (Task 4 Step 3 asks for this) — the 100-paragraph cap is the plan's own suggested starting point, not a measured value. If it is too slow even at 100, lower it; if it has headroom, this is a candidate to raise later.
