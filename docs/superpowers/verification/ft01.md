## Post-hoc fix: settings button completely unresponsive (2026-08-24, user-reported)

**Symptom:** clicking the gear/settings button in the header did nothing at all - no dropdown, no error.

**Root cause:** two separate `settingsBtn.addEventListener('click', ...)` registrations existed on the same button - the original pre-FT-1 handler (unconditionally toggling `#settingsPanel`'s `.open` class) was never removed when FT-1's Task 1 Step 4 added its own consolidated handler (which does the same toggle in chat view, plus doubles as "back to conversation" in the settings view - its own comment literally says "one handler, not two rebound listeners", but the old one was left in place). Every click fired both: the first toggled `.open` on, the second (seeing `inSettingsView === false`) toggled it right back off in the same event - a net no-op on every single click.

**Fix:** removed the stale first listener; the second (already-correct) one covers everything the first did.

**Why no existing test caught this:** every prior settings-related test either clicked the button once and then interacted directly with the panel's fields (bypassing whether the panel was actually visibly toggled open), or exercised the *separate* settings-view path (`#moreSettingsBtn` → `openSettingsView()`), never asserting the quick dropdown's own open/closed state via the gear button in ordinary chat view - the one path where two competing toggles could cancel out. Added a regression test (`chat-ui.test.ts`, "the gear button toggles the quick settings dropdown open and closed in chat view") that asserts `#settingsPanel`'s `.open` class directly across two clicks - the toggle-cancels-toggle bug fails this test immediately.

**Verification:** `npx vitest run` - 42/42 (41 prior + 1 new), all three bundles rebuild, all three `tsc --noEmit` clean, all three `MSBuild` clean.

## Post-hoc fix 2: "More settings" button visible inside the settings view it opens (2026-08-24, user-reported)

**Symptom:** once inside the full settings view, the "More settings" button (whose whole purpose is to *get* there) was still showing - confusing, since clicking it again does nothing useful from inside the view it already opens.

**Root cause:** `openSettingsView()`/`closeSettingsView()` correctly set `moreSettingsBtn.hidden = true`/`false` - that part of the JS was always right. The bug is CSS: `.ai-more-settings-btn` has its own `display: block` rule (needed for its normal layout in the quick dropdown), which has the *same specificity* as the browser's built-in `[hidden] { display: none }` rule. Since the app's own stylesheet loads after the browser's UA stylesheet, the author rule wins the cascade - so setting `.hidden = true` had no visual effect at all. This is a generic gotcha, not specific to this fork's work: any element with its own unconditional `display` rule needs an explicit `[hidden]` override to make `element.hidden` actually work.

**Fix:** added `.ai-more-settings-btn[hidden] { display: none; }` in `chat-ui.css` - a compound selector has strictly higher specificity than the plain class rule, so it wins regardless of source order, no `!important` needed.

**Important limitation on the test I added:** `chat-ui.test.ts`'s "More settings opens the settings view..." test now also asserts `moreSettingsBtn.hidden` (`true` inside the view, `false` back in chat), but **this only checks the HTML `hidden` attribute, not whether CSS actually renders it hidden** - jsdom does not compute cascaded styles from loaded stylesheets the way a real browser does, so this specific class of bug (JS attribute correct, CSS silently overriding its visual effect) is not something vitest can catch. The test is honest value (confirms the JS-side intent), not a guarantee against a CSS regression of this exact kind. Real-browser confirmation matters specifically for this fix.

**Verification:** `npx vitest run` - 42/42 (assertions added to an existing test, not a new one, so the count is unchanged from fix 1). All three bundles rebuilt (`bundle.css.map` grew, confirming the CSS change was actually bundled) and MSBuild clean.

## Deviations from plan

- **Task 4/Task 9 reconciliation:** the plan's own text has Task 4 stating registration "takes effect right away" (live, via `onToolRegistrationChange`) while Task 9 lists tool registration among the things Save "applies together." Implemented registration as live/immediate (matching Task 4's own stated verification method — "toggling a tool off removes it from `activeTools()`"); `registeredTools` in the extended `onSettingsSave` payload is an inert echo, not the actual application path. Documented inline in `chat-ui.ts`.
- **Task 7's abstract `PaneHostBase` hooks don't exist.** The plan's Task 7b snippet assumes `DocumentPath`/`DocumentFullName`/`ProvisionalId` abstract members on `PaneHostBase` (citing "PP-0 Task 8 Step 2"). The as-built PP-1 never added these — each `TaskPaneHost.cs` has its own concrete, inline `_document`/`_workbook`/`_presentation` field and `GetChatId()` override. Implemented the re-keying logic directly inside each of the three `GetChatId()` methods instead (the plan's own stated fallback: "or the three `TaskPaneHost.cs`").
- **`GetChatId()` access.** It is `protected`, and `ThisAddIn.cs` is not a subclass of `PaneHostBase` (same assembly ≠ inheritance relationship in C#), so it cannot call `GetChatId()` directly to force Task 7b Step 2's pre-disposal re-key check. Added a `public void FlushChatIdMigration()` wrapper to `PaneHostBase` instead of widening `GetChatId()`'s own visibility.
- **Tool counts differ from the plan's estimate** ("Word 7, Excel 10, PowerPoint 23" — Task 5 Step 3): actual counts as of this pass are Word 8 (`get_document_context`, `insert_content`, `edit_chart`, `read_blocks`, `replace_blocks`, `add_image`, `apply_commands`, `add_comment`), Excel 10 (matches), PowerPoint 26. Every tool in `ALL_WORD_TOOLS`/`ALL_TOOLS`/`ALL_TOOLS` (PowerPoint) has a `toolDisplay` entry; none rely on the fallback-to-raw-name path.
- **Hebrew text is machine-authored, not reviewed by a Hebrew speaker.** Per Task 5 Step 6, this is flagged rather than treated as done — all ~40 `toolDisplay` entries' Hebrew label/description, plus the smaller FT-2 vocabulary added to `chat-ui.ts`'s `STRINGS` (`scopeColumn`, `scopeRowsWithData`, etc.), need a native-speaker pass before shipping.
- **PP-6's provider/settings shape** (unchanged by FT-1, carried forward as context for FT-2/future work): `PanelSettings { ai: AiSettings; skipTlsVerify }`, default provider `'custom'`, per-provider remembered values keyed by `AiProviderId`. See `pp06.md` for the full account.
