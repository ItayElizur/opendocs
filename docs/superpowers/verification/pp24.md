## What got resolved at real compile time (grounded correctly this time)

Every enum member and method signature in this plan was pre-confirmed via .NET reflection against the actual referenced `Microsoft.Office.Interop.PowerPoint.dll` before being written into code — the direct lesson from PP-9/PP-23's chart-bug saga (three rounds of guessed COM signatures). That grounding held: **all curated enum maps compiled on the first attempt, with zero incorrect member names.**

One real compile-time correction was still needed, caught by an actual MSBuild error rather than guessed:

- **`Sequence.Item` is a COM indexed property, not a callable method.** `sequence.Item(i)` failed with `CS1061: 'Sequence' does not contain a definition for 'Item'`. Reflection confirmed the member exists as `get_Item(Int32)` returning `Effect` — the correct C# access is the indexer syntax `sequence[i]`, not a method call. Fixed in both `ReadAnimations` and `EditAnimation`. (This is a routine COM-interop indexer quirk, not evidence the earlier reflection was wrong — `Item` genuinely exists on the type, just not as `.Item(...)`.)

## Still genuinely unverified — flagged honestly in the plan itself, not discovered after the fact

Two behaviors could not be confirmed by reflection (which reveals signatures, not runtime semantics) and need a live PowerPoint session:

1. **`Sequence.AddEffect`'s trailing `Int32` parameter's `-1`-means-append behavior.** Documented in Microsoft's own reference, not independently re-derived. If wrong, the safe fallback (noted in the plan) is `sequence.Count + 1` instead of `-1`. **Test this first** — create 2-3 animations on the same slide in one session and confirm they land in the order added, not reversed or erroring.
2. **`Effect.MoveTo`'s exact indexing convention** for `edit_animation`'s `reorder` kind. Confirmed to exist via reflection; its precise 1-based-vs-something-else semantics were not. If it lands one position off, the fallback is `MoveBefore`/`MoveAfter` (relative-position moves against another `Effect` reference, also confirmed to exist).

Everything else in this plan is statically-typed, non-`dynamic` C# against interop types this project already references elsewhere — no `dynamic`-COM risk class at all, unlike Word's chart/SmartArt code.
