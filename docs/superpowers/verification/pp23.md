# PP-23 — Word Table and SmartArt Support (+ PowerPoint read-visibility fix) — Verification

**Scope covered:** all 8 tasks — `add_table`/`edit_table`/`read_table`, `add_smartart`/`edit_smartart`/`read_smartart` (Word), schema/toolDisplay/system-prompt integration, manual matrix, and Task 8's PowerPoint `ShapeText` fix.

## Post-hoc fixes (2026-08-24, user-reported, from the first real hands-on test of this plan)

Four real bugs, all confirmed by the user's own testing and fixed:

1. **Chart: same `0x800706BE` RPC failure as before, plus the chart visibly "jumped" to the correct data only after opening Edit Data, and the embedded workbook's highlighted source scope still showed the original placeholder extent.** Root cause: `WriteChartData` (Word) / `AddChartPpt` (PowerPoint) bound the chart to `sheet.UsedRange`, read immediately after `Cells.Clear()` + a bulk `Value2` write. `UsedRange` is cached/lazily recomputed by Excel and was not reliably refreshed by the time `SetSourceData` ran on this call path - the chart bound to a stale range, and only "jumped" once the user's own Edit Data interaction forced Excel to resettle it. Fixed by building the source range explicitly from the cells just written (`sheet.Range(topLeft, bottomRight)`) instead of querying `UsedRange` at all. Additionally wrapped the whole Clear+write+SetSourceData sequence in a new `RetryTransientCom` helper (3 attempts, short backoff) that retries only on the specific known transient RPC HRESULTs (`0x800706BE`, `0x8001010A`, `0x800706BA`) - a documented, standard mitigation for this class of embedded-OLE-server flakiness, not a guaranteed fix. Applied identically in both `WordTools.cs` and `PowerPointTools.cs`.
2. **Table borders: `edit_table` with `kind:'set_style', borders:true` did nothing.** Root cause: a real design gap, not a user error - the `set_style` branch never had border support at all (only `styleName`/`headerRow`/`bandedRows`), so the model's `borders:true` call (a reasonable guess, since `updateParagraphStyle` elsewhere in this same tool surface already uses exactly that field name/shape) matched nothing and silently no-opped. Fixed by adding `borders`(bool)/`borderColor`(hex, default black) to `set_style`, applied via `table.Borders` (the same `Word.Border` collection type `updateParagraphStyle` already uses for paragraph borders). Schema and description updated in `entry.ts`.
3. **SmartArt creation showed a pile of "[Text]" placeholder nodes above the real ones.** Root cause: exactly the chart bug's shape again - `Shapes.AddSmartArt` seeds the new diagram with the layout's own default placeholder nodes (the same "[Text]" prompts the ribbon's gallery shows), and `AddSmartArt`'s handler only ever *appended* new nodes, never clearing the pre-seeded ones first. Fixed by deleting every existing node (`smartArt.Nodes.Item(i).Delete()`, iterating backward) before adding the requested items, in both `WordTools.cs` and `PowerPointTools.cs` (PowerPoint had the identical latent bug, unreported until found while fixing Word's).
4. **`read_smartart`/`edit_smartart` always reported "No SmartArt diagrams in this document", even immediately after `add_smartart` had just created one.** Root cause: exactly the risk `pp23.md`'s own first draft flagged before any testing (see below) - `HasSmartArt` returns an `MsoTriState`, not a real C# `bool`, the same as `HasChart` elsewhere in this file (which already needed `(int)shp.HasChart == -1` instead of a bool cast, from PP-9). `ListSmartArtShapes`'s `(bool)shp.HasSmartArt` cast either threw (silently swallowed by its own `try/catch`) or never matched, so no shape was ever recognized as SmartArt by the read/edit path - `add_smartart` itself worked because it holds a direct shape reference and never goes through this detection at all. Fixed with the same `(int)x == -1` comparison `HasChart` already uses, in both `WordTools.cs`'s `ListSmartArtShapes` and `PowerPointTools.cs`'s new (Task 8) `ShapeText` branch.

**Verification:** `MSBuild` clean (Word + PowerPoint), `tsc --noEmit` clean, bundle rebuilds, vitest 42/42 and `dotnet test` 23/23 unaffected. **None of these four fixes have been re-tested against real Office yet** - they were diagnosed from the user's precise symptom descriptions and fixed at the identified root cause, but the next real test is what actually confirms them. Fix #1's retry wrapper in particular only reduces the odds of hitting the transient RPC failure; it does not guarantee it can never recur.

## Round 2 post-hoc fixes (2026-08-24, user-reported after re-testing round 1)

The chart fix above did NOT resolve the chart bug - the user re-tested and hit the identical symptom. Five more real issues, all fixed:

1. **Chart bug recurred identically (same RPC error, same wrong-scope-until-Edit-Data symptom) despite round 1's fix, plus `read_chart` "still doesn't work".** Since switching from `UsedRange` to an explicitly-built `sheet.Range(topLeft, bottomRight)` did not change the outcome, the failure is evidently not (only) about `UsedRange` staleness - it recurs identically regardless of how the range is built, which points at the embedded OLE workbook's automation surface not always being fully ready the instant `ChartData.Workbook` returns (a separately documented class of embedded-chart flakiness). Three changes, all defense-in-depth since none could be confirmed as *the* root cause without a live session: (a) added a 120ms settle delay before the first COM call against the freshly-opened workbook, inside the retry loop so every attempt gets one; (b) reuse `writeRange` (the already-proven `Resize[]` result from the data write itself) directly for `SetSourceData` instead of constructing a second, separate Range object - one fewer COM object construction on the failure path; (c) widened `RetryTransientCom`'s catch from `COMException` specifically to the base `Exception` type (still HResult-filtered) - a COM error surfaced through `dynamic` late-binding is not guaranteed to arrive as a raw `COMException`, so the retry may simply never have been triggering. Also wrapped `ReadChart`'s previously-unprotected embedded-workbook read in the same `RetryTransientCom` + settle delay, since the user's "read chart still doesn't work" report point at the identical class of failure on the read path. **Honesty note:** unlike every other fix in this file, this one could not be traced to a single confirmed root cause - it is the best defensible next iteration, not a verified fix. If it recurs a third time, the next step needs the *exact* exception text/stack from a live session, not another guess.
2. **Table borders: black border request also drew crisscrossing diagonal lines across every cell.** Root cause: `table.Borders` is not just the 6 grid sides - Word's `Borders` collection for a table also includes `wdBorderDiagonalDown`/`wdBorderDiagonalUp` (the rare cell-split diagonal lines), and round 1's `foreach (Word.Border border in table.Borders)` blindly turned every member on, diagonals included. Fixed by enumerating only the 6 real grid sides (`wdBorderTop/Left/Bottom/Right/Horizontal/Vertical`) explicitly via `table.Borders[side]`.
3. **`read_smartart` required one call per diagram; user asked for a way to read all of a document's SmartArt text at once.** Not a bug, a requested convenience. `ReadOneSmartArt` extracted from the per-diagram body; `ReadSmartArt` now reads every diagram in the document (joined with blank lines) when `smartArtIndex` is omitted, rather than defaulting to "just the first one." Schema description updated accordingly.
4. **SmartArt had no way to change color/style on an existing diagram.** Real feature gap - `edit_smartart` had no such `kind` at all. Investigated via .NET reflection against the actual referenced Office 15 PIA (`Office.dll`) rather than guessing: confirmed `Microsoft.Office.Core` has **no** `MsoSmartArtColorType`/`MsoSmartArtQuickStyleType` enum at all (unlike what the analogous chart/layout code might suggest) - color schemes and quick styles are live COM collections (`Application.SmartArtColors`/`.SmartArtQuickStyles`, each item exposing `.Name`), the same *shape* as `SmartArtLayouts` but populated at runtime by the install's own gallery, not a fixed enum. Rather than guess exact display-name strings (unverifiable and risking a wrong-but-silently-"successful" style), added `edit_smartart`'s new `set_style` kind (`colorName?`, `quickStyleName?`) resolved by case-insensitive **substring match** against whatever names this install's live gallery actually has - a miss lists the real available names so the model can retry correctly instead of guessing blind. `smartArt.Color`/`.QuickStyle` are the corresponding settable properties (confirmed via the same reflection pass).
5. **Selecting a table, chart, or SmartArt object did not appear under "Selection:" at all** (an actionable pointer the user explicitly asked for). Root cause: Word's selection context was purely text-based (`selection.Text` for a shape/table selection is empty or a placeholder character) - the one selection kind, unlike Excel/PowerPoint's, with no object-level addressing at all. `TaskPaneHost.OnSelectionChanged` now detects a table selection (via `wdWithInTable` + matching `Range.Start` against `ActiveDoc.Tables`) or a selected chart/SmartArt shape (via `HasChart`/`HasSmartArt`, matched by `.Name` against `WordTools.ListChartShapes`/`ListSmartArtShapes` - both promoted from `private` to `internal` so this new code can reuse them rather than duplicating the MsoTriState-comparison logic a second time) and reports the SAME 0-based index the read/edit tools would use. Threaded through as a new `wordObject` `SelectionExtent` kind in `chat-ui.ts` (renders as e.g. "Table 2" in the pill) and a new branch in `defaultDescribeSelection` (tells the model to call `read_table`/`read_chart`/`read_smartart` with that exact index before editing).

**Verification:** `MSBuild` clean (Word + PowerPoint), `tsc --noEmit` clean in all three apps (chat-ui/bootstrap.ts/bridge.ts are shared), all three bundles rebuild, vitest 42/42, `dotnet test` 23/23. **None of round 2 has been tested against real Office either.** Item 1 in particular is explicitly *not* claimed as fixed with confidence - see its own honesty note above.

## What got resolved at real compile time (higher confidence than the plan assumed)

The plan flagged two specific Word table API uncertainties as "verify during implementation." Both were resolved by an actual MSBuild run, not guessed:

1. **`Document.Tables.Add(Range, rows, cols)`** compiles with exactly 3 arguments — no `Type.Missing`/named-optional-argument workaround needed for the trailing `DefaultTableBehavior`/`AutoFitBehavior` parameters in this project's PIA.
2. **`Table.Style` assignment must go through `set_Style(string)`**, not a `Style =` property setter — `error CS1545: Property, indexer, or event 'Table.Style' is not supported by the language`. Fixed (`WordTools.cs`, `EditTable`'s `set_style` branch) using the same `set_Style` pattern already used elsewhere in this file (`p.Range.set_Style(...)`).
3. **The banded-rows toggle is `Table.ApplyStyleRowBands`, not `Table.ApplyStyleBandedRows`** (the plan's guessed name, by analogy with PowerPoint's `HorizBanding`) — `error CS1061`. Fixed. `Table.ApplyStyleHeadingRows` (the header-row toggle) compiled as originally written — the plan's guess for that one was correct.

All three came from real `MSBuild.exe` errors against `Microsoft.Office.Interop.Word`, then fixed and re-verified with a second clean build — not left as runtime-only guesses.

2. **`floatingAtAnchor.ConvertToInlineShape()`** on the SmartArt shape — same untested assumption as PP-9's chart-anchoring code.
3. ~~`shp.HasSmartArt` cast to `bool`~~ — **confirmed wrong by the first real test and fixed** (see Post-hoc fixes #4 above): `HasSmartArt` does need the `MsoTriState`-shaped comparison, exactly as flagged here before any testing happened. Left as a record of a risk that was correctly predicted, not removed.
4. **`nodes.Item(i)` vs `nodes[i]`** indexer form on the SmartArt `Nodes` collection (`WordTools.cs`'s `ReadSmartArt`/`EditSmartArt`, and the analogous read in `PowerPointTools.cs`'s `ShapeText` branch) — both plausible; wrong form throws `RuntimeBinderException` at runtime. **Still unverified** - the user's `read_smartart`/`edit_smartart` test never reached this code at all, since it failed earlier at the `HasSmartArt` detection bug (#3, now fixed). This is the next thing to actually exercise.
5. **`Microsoft.Office.Interop.Word.Application.SmartArtLayouts`** — assumed to exist and behave identically to PowerPoint's already-proven `Globals.ThisAddIn.Application.SmartArtLayouts`, since SmartArt is documented as the Office-shared object model. Not cross-checked against this Word PIA specifically, though `add_smartart` creating diagrams successfully (per the user's report) confirms this part already works.

None of these affect the table tools (Tasks 1-3), which are statically typed throughout and therefore already have real compile-time confirmation beyond what the plan expected.
