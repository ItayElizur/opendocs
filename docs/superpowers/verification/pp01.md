# PP-0 (Tasks 7-9) + PP-1 — Verification

**Scope covered:** PP-0's deferred C# extraction (`RibbonBase`, `PaneHostBase` in `OfficeAi.Shared`) and PP-1 in full (per-window pane registry, per-document chat id and editing mode, ribbon toggle targeting the active window).

## Post-hoc fix: WebView2 init race (2026-08-24, found via real Office testing)

The "Unverified-by-construction risk" section below (written before any real testing) predicted exactly this failure mode. It was hit on the very first real test, with only a **single** document open in Excel and PowerPoint (Word, tested first, happened not to trigger it) — narrower than originally predicted (which framed the risk as an N-panes/multi-window concern), so the write-up below is corrected accordingly.

**Symptom:** Excel showed the pane's status label as `WebView2 init failed: The group or resource is not in the correct state to perform the requested operation. (Exception from HRESULT: 0x8007139F)`. PowerPoint showed a blank pane with no visible error.

**Root cause:** `OfficeAi.Shared/WebViewBridgeHost.cs`'s `InitializeAsync` called `CoreWebView2Environment.CreateAsync(null, userDataFolder)` fresh on every construction. Before PP-1 there was exactly one `TaskPaneHost`/`WebViewBridgeHost` per process, so this was only ever called once — never exercised. PP-1 made per-window panes possible, and `EnsurePaneFor` had no reentrancy guard: `CustomTaskPanes.Add` can pump the Windows message queue internally, which lets a nested `WindowActivate` for the *same* window being set up reenter `EnsurePaneFor` before the outer call has returned and written `_panes[hwnd]` — producing two `TaskPaneHost`/`WebViewBridgeHost` instances for one window, both racing to create a `CoreWebView2Environment` against the identical user-data folder. WebView2 rejects a second concurrent `CreateAsync` for a folder whose first call hasn't finished with exactly this HRESULT. This explains both symptoms: Excel's crash is the losing call's exception; PowerPoint's blank pane is consistent with the *visible* pane being the one that lost the race (never reaching `_webView.Source = ...`), while the winning pane exists but isn't the one shown.

No stray `msedgewebview2.exe` processes or Application-event-log entries were found at the time (checked directly) — ruling out a leftover-process/lock explanation and pointing at the in-process race above.

**Fix, two parts (both needed — one closes the race by construction, the other stops wasted duplicate pane creation at the source):**

1. `OfficeAi.Shared/WebViewBridgeHost.cs` — added `GetOrCreateEnvironment(appDataFolderName)`, caching the in-flight `Task<CoreWebView2Environment>` (not just the eventual result) in a `static Dictionary<string, Task<CoreWebView2Environment>>`, keyed by app-data-folder name and shared by every pane in the process. A second constructor's synchronous check-and-insert (before any `await`) sees the dictionary already populated and awaits the same task instead of starting a second `CreateAsync`. This is also the officially documented WebView2 pattern (share one environment across multiple controls against one profile), not just a race-avoidance hack. Only ever touched from the single STA UI thread all Office COM callbacks run on, so no lock is needed.
2. All three `ThisAddIn.cs` — added `_paneCreationInProgress` (a `HashSet<int>`) to `EnsurePaneFor`: `HashSet<T>.Add` returns `false` if the hwnd is already being set up, so a reentrant call bails out (returns `null`) instead of constructing a second `TaskPaneHost`/`CustomTaskPane`. `TogglePane()` null-checks the result accordingly.

**Verification:** all four C# projects rebuild clean (checked via full `MSBuild.exe`, not just `dotnet build`); `dotnet test` — 8/8 passed, both before and after.

**Retest after this fix:** the WebView2 race/blank-pane symptoms persisted. Full close/reopen confirmed the new DLL was loaded (still hit the failure), and the user reported the actual trigger: Excel/PowerPoint were launching to Office's own "Start Screen" (the gray template-chooser shown before any real workbook/presentation exists), requiring Ctrl+N/File>New to reach a real document. Word's earlier working test had opened real `.docx` files directly, never landing on this screen - explaining the Word/Excel-PowerPoint asymmetry without needing a different root cause per app.

## Post-hoc fix 2: unguarded startup `EnsurePaneFor` call (2026-08-24)

**Root cause:** `ThisAddIn_Startup` calls `EnsurePaneFor(this.Application.ActiveWindow)` **eagerly, with no null-check and no try/catch** - the only `EnsurePaneFor` call site not defended this way (every other one, `Application_WindowActivate` and `TogglePane`, already wraps it). On Excel's/PowerPoint's Start Screen, no workbook/presentation exists yet, so `Application.ActiveWindow` is either null or a transient pseudo-window that doesn't behave like a normal `Excel.Window`/`PowerPoint.DocumentWindow` when its properties are read (e.g. `.Hwnd`/`.Parent`) - either way, unguarded, this could throw out of `ThisAddIn_Startup` or construct a pane against a degenerate window reference, consistent with the observed blank/gray pane.

**Fix:** wrapped the startup call in all three `ThisAddIn.cs` with a null-check plus `try/catch`, matching every other call site's existing defensive pattern:

```csharp
try
{
    Excel.Window active = this.Application.ActiveWindow;   // Word.Window / PowerPoint.DocumentWindow in the other two
    if (active != null) EnsurePaneFor(active);
}
catch { }
```

If `ActiveWindow` is null or throws on the Start Screen, no pane is created for it at all - by design, since it isn't a real document window. `Application_WindowActivate` still creates a proper working pane the moment a real document exists (Ctrl+N, File > Open, etc.), regardless of whether the startup call succeeded.

Applied to Word too (not just Excel/PowerPoint) since Word can show the same Start Screen when launched without a specific file - the earlier working test happened to open real files directly, which bypasses it, so this was latent there too, not actually Word-specific-safe.

**Verification:** all three apps rebuild clean. **Confirmed working by the user (2026-08-24):** "all three file types work even with multiple windows open" - both fixes together resolved the Start Screen blank-pane issue and the WebView2 init race, and the original multi-window ribbon-toggle bug that motivated PP-1 is fixed.

**Not runtime-verified by this agent.** No interactive Office session is reachable from this environment. Everything below the automated-checks section is a manual matrix for a human to run; do not treat "builds clean" as "works."

## Deviations from plan

1. **`OfficeAi.Shared.EditingMode` is a new shared type**, not called for explicitly in PP-0/PP-1's text. `PaneHostBase.SetEditingMode(EditingMode mode)` needs one concrete `EditingMode` type to dispatch through, but Word/Excel/PowerPoint each declared their own identical-but-separate `public enum EditingMode {...}` in their own namespace. Replaced all three with one declaration in `OfficeAi.Shared` (`PaneHostBase.cs`); each `*Tools.cs` now resolves `EditingMode` via its existing `using OfficeAi.Shared;`. This removes rather than adds duplication, in the same spirit as the rest of PP-0/PP-1, but it is a change beyond what either plan's text specified — flagging it explicitly rather than treating it as an unremarkable implementation detail.

2. **`OfficeAi.Shared.csproj` needed new reference-resolution plumbing** to compile `RibbonBase.cs` (which needs `Microsoft.Office.Core.IRibbonExtensibility`/`IRibbonUI`/`IRibbonControl` and `stdole.IPictureDisp`). This project had never referenced Office/stdole before — every prior file in it (`ChatStore`, `ToolProtocol`, `WebViewBridgeHost`) was Office-agnostic. Two things were needed together, because the two build tools available disagree on resolution:
   - `AssemblySearchPaths` in the `.csproj` gained `{AssemblyFolders};{GAC};{Registry:Software\Microsoft\.NETFramework,v4.8,AssemblyFoldersEx}` — this project is SDK-style (`Microsoft.NET.Sdk`) and its default search paths omit these, unlike the apps' legacy-style `.csproj`, which is why plain GAC-identity references (`Office, Version=15.0.0.0,...` / `stdole, Version=7.0.3300.0,...`, no `HintPath`) resolve for the apps but not for this project without the addition.
   - Even with that fix, `dotnet build`/`dotnet test` (used to run `OfficeAi.Shared.Tests`) still failed to resolve both references — its resolver does not appear to honor the same search-path tokens the full `MSBuild.exe` does for this project shape. Added explicit `HintPath`s as a fallback (MSBuild tries `HintPath` first, falls through to the search-path tokens if absent — so this degrades gracefully on a machine where the hardcoded path doesn't exist). One wrinkle: `...\Common7\IDE\PublicAssemblies\stdole.dll` on this machine is `stdole` **v17.0.0.0**, not the requested v7.0.3300.0 (a newer, unrelated `stdole` shipped alongside VS2022 tooling) — the correct v7.0.3300.0 lives in the classic `.NET Framework` GAC hive at `C:\Windows\assembly\GAC\stdole\7.0.3300.0__b03f5f7f11d50a3a\stdole.dll` (note: `GAC`, not `GAC_MSIL` — a different, older hive that `dotnet build`'s resolver apparently doesn't search even via the `{GAC}` token). Both hardcoded paths are specific to this machine's install layout; if they don't exist on another machine, either toolchain still has the `AssemblySearchPaths` fix as a fallback path for full-MSBuild builds, but `dotnet test` may need its `HintPath` values updated to match wherever that machine's PIAs live.

3. **`PaneRegistry<TWindow>` generic — not attempted, per the plan's own sanctioned fallback.** With all three inline registries built, the concrete differences are larger than "different window types": the hwnd property is even spelled differently (`Word.Window.Hwnd` / `Excel.Window.Hwnd` / `PowerPoint.DocumentWindow.HWND`, note the casing), document resolution differs in shape (`window.Document` / `(Excel.Workbook)window.Parent` / `window.Presentation`), and the close-event signature itself differs (Word's `DocumentBeforeClose`/Excel's `WorkbookBeforeClose` both carry `ref bool cancel`; PowerPoint's `PresentationClose` does not). A generic could only share the ~25-line `Dictionary<int,PaneEntry>` + `EnsurePaneFor`/`ApplyPaneWidth` core; each `ThisAddIn.cs` would still need nearly as much per-app glue bridging COM-specific names/casing/event shapes into the generic's delegates. Judged not a good trade — three inline copies kept, as PP-1's added note (originating in PP-0 Task 9) explicitly allows.

## Known, deliberately out-of-scope limitation

**PP-1 Task 5 Step 5:** every COM executor (`WordTools.ActiveDoc`, `ExcelTools.Sheet(...)`, `PowerPointTools.ActivePresentation`) resolves the *currently active* document/workbook/presentation, not necessarily the one whose pane issued the tool call. A user who switches windows mid-run would have that run's remaining tool calls act on the newly-active document instead of the one the run started against. Documented with an identical comment at each resolution point; fixing it needs per-document COM target resolution across every executor method in all three `*Tools.cs` files, which the plan explicitly scopes out as a separate, larger change.

## Unverified-by-construction risk (flagged, not fixed)

**Shared WebView2 user-data folder across N panes in one process.** `WebViewBridgeHost`'s `userDataFolder` is `LocalApplicationData\<appDataFolderName>\WebView2` — the same path for every pane within one app, since `appDataFolderName` is fixed per app, not per window. Multiple WebView2 controls in one process sharing one user-data-folder is a normal, supported WebView2 pattern (analogous to multiple tabs in one browser process), so this is expected to work without changes — but it has not been tested here. If a second window's pane shows a WebView2 init error in its status label instead of reaching `ready`, that is the signal this assumption was wrong; the fix would be giving each pane its own subfolder keyed by hwnd, per PP-1 Task 6 Step 3.
