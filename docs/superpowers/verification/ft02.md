## Post-hoc fix (2026-08-24, user-reported)

**Bug, confirmed and fixed:** Word's `text` selection kind was the one FT-2 left un-addressable - Excel's `range` kind carries an A1 address, PowerPoint's `slides`/`shapes`/`shapeText` kinds carry indices, but Word's carried only `preview`/`fullText`, no position at all. Symptom: the user selected a paragraph and asked to translate it; the model translated correctly but had no way to call `replace_blocks` on exactly the selected paragraph(s) (no index to give it), so it fell back to `insert_content`, appending the translation as a new paragraph instead of replacing the original.

**Fix:** `WordAiAddIn/TaskPaneHost.cs`'s `OnSelectionChanged` now computes the 0-based paragraph range (`startBlockIndex`/`endBlockIndex`) the selection spans, by walking `selection.Document.Paragraphs` and comparing character offsets against each paragraph's `Range.Start`/`.End`. Threaded through `bridge.ts`'s `RawSelectionPayload` and `bootstrap.ts`'s `SelectionContext` (`text` variant gains the two fields); `defaultDescribeSelection`'s `text` case now states the range explicitly and tells the model to prefer `replace_blocks` with those indices over `insert_content`, matching the addressable-wording pattern the `range`/`slides`/`shapes` cases already used.

**Verification:** `tsc --noEmit` clean in all three apps, all three bundles rebuild, `shared/chat-ui` vitest 42/42 and `OfficeAi.Shared.Tests` 23/23 unaffected (neither touches this code path), `WordAiAddIn` MSBuild clean. **Not verified against a live Word session** - the paragraph-index-from-character-offset walk (`selection.Start < r.End` / `selection.End <= r.End`) has an inherent edge case worth checking manually: a selection whose end lands exactly on a paragraph boundary (e.g. selecting through the very end of a paragraph including its paragraph mark) - confirm `endBlockIndex` lands on the paragraph the visible selection appears to end in, not one past it.

## What was built

- `OfficeAi.Shared/PaneHostBase.cs` (Task 1): `PostSelection(payload, signature)` — a `System.Windows.Forms.Timer` (UI-thread, no cross-thread marshaling) debounces at 200ms, restarting on every call and only actually posting on tick; an identical `signature` to the last one *posted* is dropped immediately without even restarting the timer. `Dispose(bool)` override added (none existed before) to stop/dispose the timer.
- `WordAiAddIn/TaskPaneHost.cs`: `OnSelectionChanged` now calls `PostSelection(..., "word:" + start + "-" + end)` instead of `PostMessage` directly — the only behavior change is debouncing; payload shape unchanged.
- `ExcelAiAddIn/ThisAddIn.cs` + `TaskPaneHost.cs` (Task 2): wired `Application.SheetSelectionChange`, routed to the pane via `Application.ActiveWindow.Hwnd`. Payload reports the literal address/extent (`CountLarge`, not `Count` — avoids `Int32` overflow on a whole-sheet selection) plus `entireColumns`/`entireRows` classification and, when those are true or the selection exceeds 10k cells, an `Intersect(target, sheet.UsedRange)`-derived `effectiveAddress`/`effectiveCellCount`/`effectiveRows`/`effectiveCols` (added beyond the plan's own snippet — see Deviations). A null/non-Range selection (chart/shape) posts `hasSelection: false` rather than throwing.
- `PowerPointAiAddIn/ThisAddIn.cs` + `TaskPaneHost.cs` (Task 3): wired `Application.WindowSelectionChange`, routed via `Sel.Parent as DocumentWindow` falling back to `Application.ActiveWindow`. Branches on `Sel.Type` into three payload shapes (`selKind: "slides" | "shapes" | "shapeText"`), converting every 1-based COM index to 0-based exactly once at this boundary. Shape identity within a slide (needed since `Sel.ShapeRange` doesn't carry the tools' 0-based `Shapes` collection position) is resolved via a `shape.Id` search (`ShapeIndexInSlide`), not `Name` (not guaranteed unique). Shape-text previews are capped at 80 chars / 5 shapes and check `HasTextFrame`/`TextFrame.HasText` before reading `TextRange.Text`.
- `shared/web-src/app-shell/bridge.ts` (Task 4): `RawSelectionPayload` — the raw, app-tagged WebMessage shape (superset covering Word/Excel/PowerPoint's distinct fields); `BridgeHandlers.onSelectionChanged` widened to take it.
- `shared/web-src/app-shell/bootstrap.ts` (Task 4): `SelectionContext` discriminated union (`none`/`text`/`range`/`slides`/`shapes`/`shapeText`), `toSelectionContext()` (raw payload → context), `defaultDescribeSelection()` (context → the per-turn sentence, kind-keyed rather than per-app-configurable — see Deviations), `toSelectionScopeUpdate()` (raw payload → the UI's `SelectionExtent` classification, Task 5's "shell computes" half). `buildContext()` now reads `describeSelectionFn(latestSelectionContext)`, captured once per run (unchanged from Word's existing per-run contract — explicitly NOT `systemSuffix`, which is FT-1's per-turn document guidelines).
- `shared/chat-ui/chat-ui.ts` (Task 5): `SelectionExtent` union (`cell`/`range`/`wholeColumn`/`wholeColumns`/`wholeRow`/`multiArea`/`slides`/`shapes`/`shapeText`) and `buildExtentLabel()` — localizes and renders the pill text from the shell's structured classification, so a language switch relocalizes it for free via the existing `refreshScopeHint()` (already called from `setLang`). `setSelectionScope`'s parameter widened to `{ hasSelection, preview?, extent? }` (Word keeps `preview`, wrapped in the now-STRINGS-driven `scopeSelectionPrefix` + quotes/ellipsis; Excel/PowerPoint use `extent`, rendered as-is with no quoting). New `scopeUnit` mount option (`'doc' | 'sheet' | 'deck'`) picks the "no selection" wording; `WordAiAddIn` defaults to `'doc'` (unset), Excel passes `'sheet'`, PowerPoint `'deck'`.
- `WordAiAddIn/web-src/entry.ts`: unchanged (`useSelectionContext: true` was already set). `ExcelAiAddIn/web-src/entry.ts` / `PowerPointAiAddIn/web-src/entry.ts`: added `useSelectionContext: true, scopeUnit: 'sheet' | 'deck'`.
- `shared/chat-ui/chat-ui.test.ts`: 7 new tests — extent-vs-preview rendering (no quotes/ellipsis on an extent), single-cell bare address, whole-column/row (including the null-`dataRows` → "empty" case), multi-area, all three PowerPoint extent kinds, per-`scopeUnit` "no selection" wording, and relocalization of an active extent selection on a language switch.

## Deviations from plan

- **`SelectionContext`'s `range` variant extended beyond the plan's own sketch.** The plan's Task 4 Step 1 snippet has `{ kind: 'range'; sheet; address; cellCount; multi }`, but its own Step 2 example wording ("Only B1:B200 contains data... exceeds read_range's 2000-cell cap") requires the whole-column/row and effective-range data that snippet omits. Added `areaCount`, `entireColumns`, `entireRows`, `effectiveAddress`, `effectiveCellCount` to the variant — there is nowhere else for `describeSelection` to get this from.
- **`describeSelection` is not per-app-configurable in `entry.ts`,** despite `AddInConfig.describeSelection?` being added to satisfy the plan's stated interface. A single kind-keyed function in `bootstrap.ts` (`defaultDescribeSelection`) covers all three apps because each app's C# side only ever produces its own subset of `SelectionContext` kinds (Word: `text`/`none`; Excel: `range`/`none`; PowerPoint: `slides`/`shapes`/`shapeText`/`none`) — threading a per-app override through `entry.ts` would be unused machinery unless a future need for app-specific wording actually arises.
- **Task 5's "shell computes label" vs. Task 6 Step 3's relocalization requirement were in tension** (see the plan's own Task 5 Step 3 vs. Task 6 Step 3) — resolved by having the shell classify the raw payload into a *structured, unlocalized* `SelectionExtent` tag (numbers/kind only) and having `chat-ui.ts` own all the actual words via `STRINGS`, exactly like every other piece of text in that component. This is what makes the language-switch relocalization test (Task 6 Step 3) pass without the shell needing to re-push anything on a language change.
- **Excel's raw payload carries three fields beyond the plan's own snippet:** `areaCount` (`Target.Areas.Count`, needed for the "N areas" pill/context wording — the plan's snippet only sent a `multi: bool`), and `effectiveRows`/`effectiveCols` (the effective range's own dimensions, needed to build `wholeColumns`' "200×3 with data" label without re-parsing the `effectiveAddress` string).
- **Task 6 Step 1's literal wording** ("renders `Selection: B2:D40`") is superseded by Task 5's own later, more specific format table, which drops the "Selection:" prefix entirely for extents (`B2:D40 · 39×3`) — the table was treated as authoritative since it is strictly more detailed and was written after Step 1 in the same document.
- **PowerPoint's whole-row multi-row case, and Excel's row-extent for a multi-row whole-row selection,** are simplifications: the pill/UI only implements the single-row `row 5` form the plan's table shows; a multi-row whole-row selection reports only the first row. Not covered by the plan's table; flagged rather than guessed at length.
- **No new C# unit tests.** Task 1's debounce timer and Tasks 2/3's event handlers require a live COM host (`Excel.Application`, `PowerPoint.Application`) to construct real `Range`/`Selection` objects against, which `OfficeAi.Shared.Tests` (a plain .NET Framework unit-test project, no Office install assumed) cannot do — consistent with every other COM-facing method in this codebase (none of `WordTools.cs`/`ExcelTools.cs`/`PowerPointTools.cs`'s COM-touching methods have unit tests either; only pure-C# stores like `ChatStore`/`DocSettingsStore` do).
