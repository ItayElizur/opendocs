**Scope covered:** all 6 tasks — chart-type map, ported embedded-workbook data writer, full `edit_chart` rewrite (categories/named multi-series/chart-type/multi-chart addressing), anchored inline insertion, shared-code note (left as a comment, not extracted), manual matrix.

## Post-hoc fix + addition (2026-08-24, user-reported)

**Bug, confirmed and fixed:** creating a chart with 3 categories/1 series produced a chart with 4 categories/3 series, and the RPC call itself failed once (`0x800706BE`). Root cause: `WriteChartData` never cleared the chart's embedded workbook before writing - a brand-new chart's embedded workbook comes pre-seeded by Word/Office with placeholder sample data (a default chart template, commonly 4 categories x 3 series). Only the cells the new data occupies got overwritten; the leftover placeholder cells stayed in `sheet.UsedRange` and got plotted alongside the real data. Fixed by clearing the sheet (`sheet.Cells.Clear()`) before writing, and switching from one COM call per cell to a single batched `Range.Value2 = array` write (same pattern `ExcelTools.cs`'s `SetRangeValues` already uses) - fewer round-trips to the embedded OLE server also reduces (does not guarantee against) the kind of transient RPC failure reported. **The identical bug existed in PowerPoint's `AddChartPpt`** (the method `WriteChartData` was ported from) and has been fixed there too, before it was ever reported - same root cause, same fix.

**This also directly answers a real question the fix's own limits raised:** `edit_chart` REPLACES the whole categories/series dataset when given (not an incremental patch), so shrinking an existing chart (e.g. 5 categories down to 4) works correctly with this fix - but only if the caller sends the CORRECT remaining data. Without a way to read the chart back, the model has no way to know what to resend.

**Addition: `read_chart`, a new tool.** Reads an existing chart's title, type, categories, and per-series names/values, reusing the exact `Cells`/`UsedRange`/`.Value2` COM pattern `WriteChartData` already uses (deliberately NOT `Series.Values`/`.XValues`, whose exact marshaled array shape in this dynamic context isn't something this environment can verify). Read-only (added to `AlwaysAllowedTools` and `readOnlyTools`), addressed by the same `chartIndex` convention as `edit_chart`. System prompt updated to tell the model to call `read_chart` before an incremental `edit_chart` change.

**Verification:** `tsc --noEmit` clean, bundle rebuilds, `MSBuild` clean, `vitest` 42/42 (unaffected - no chat-ui files touched). **Both the chart-data fix and `read_chart` are `dynamic`-typed COM code, same risk category as PP-9's original anchored-insertion finding below - genuinely unverified against real Word.** The specific repro (3 categories/1 series) is the first thing worth retrying.

## Real, elevated risk — read before testing

`EditChart`/`WriteChartData` use `dynamic` throughout (an existing, deliberate pattern in this file predating this plan — "lets any signature mismatch surface immediately at runtime instead of guessing overloads at compile time"). That means **the compiler did not verify most of this method's COM calls** — only that the C# parses. Two specific things I could not confirm against a real Word session:

1. **`doc.Shapes.AddChart2(-1, type, 0, 0, 300, 200, Anchor: at)`** (the `afterBlockIndex`-anchored creation path, Task 4) — I am not certain `AddChart2` actually accepts a named `Anchor` parameter in this PIA. If it does not, this specific path (creating a chart with `afterBlockIndex` set) will throw a `RuntimeBinderException` at runtime, while every other `edit_chart` path (no position, or editing an existing chart) is unaffected. **Test this specific combination first and separately** from the rest.
2. **`floatingAtAnchor.ConvertToInlineShape()`** — assumed to exist and to inline the shape at whatever paragraph the anchor put it near. Untested.

If either fails: the safe fallback is to drop the `afterBlockIndex`-anchored-creation feature (Task 4) and keep the rest — categories/multi-series/chart-type/multi-chart-addressing (Task 1-3, which do not depend on this) work independently and are the larger share of this plan's value.

## Deviations from plan

- None of substance in Tasks 1-3. Task 4's anchored-insertion implementation is a best-effort attempt at the pattern the plan describes ("use the Shapes.AddChart2 overload that takes an Anchor range... or InlineShapes.AddChart2") — I could not confirm which of Word's actual overloads exist, so I picked the `Anchor:`-parameter-on-Shapes.AddChart2 + `ConvertToInlineShape()` route as the more standard documented pattern, but flagged it as unverified above rather than asserting it works.
- Chart index reporting after creation (`resolvedIndex`) is computed by re-scanning and comparing shape references (`shp == chartShape`) via `dynamic` `==` — this relies on COM RCW reference-equality behavior that is normally reliable within one thread/AppDomain but is not something I can guarantee. If it reports a wrong index, it is a cosmetic inaccuracy in the result text only, not a functional defect (the chart itself is created/edited correctly regardless).
