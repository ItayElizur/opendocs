## Post-hoc fix (2026-08-24, user-reported)

**Bug, confirmed and fixed:** a model that chains several tool calls back-to-back with no text in between produced a separate "Ran 1 tool" box per call instead of one box incrementing to "Ran N tools". Root cause: `bootstrap.ts`'s `onTurnEnd` handler unconditionally closed and nulled `currentToolGroup` after every turn - but `AgentLoop`'s "turn" (`shared/web-src/agent-core/loop.ts`) is one model response, which for a model calling tools sequentially is very often exactly one tool call per turn. `chat-ui.ts`'s `beginToolGroup()`/`addStep()` counting logic itself was already correct (verified by reading it first) - the bug was entirely in when bootstrap.ts chose to start a *new* group.

**Fix:** track `textStreamedSinceGroup` (set in the `onText` handler) and only close/null the group in `onTurnEnd` when text has genuinely streamed since it opened - otherwise the group stays open so the next turn's tools keep incrementing the same count. `onDone`/`onError` unconditionally close the group as a safety net (a run that ends mid-tool-chain with no trailing text still needs its group finalized). This preserves the original intended behavior for the interleaved case (tool calls, then commentary text, then more tool calls each get their own correctly-positioned group) while fixing the back-to-back case the user hit.

**Verification:** `tsc --noEmit` clean in all three apps (bootstrap.ts is shared), all three bundles rebuild, `shared/chat-ui` vitest 42/42 unaffected (no chat-ui.ts changes - the fix is entirely in bootstrap.ts's wiring). **No automated test exercises this wiring logic specifically** - `chat-ui.test.ts` tests `beginToolGroup()`'s own counting/rendering in isolation, not bootstrap.ts's decision of when to open/close a group against a live `AgentLoop`; this is a real coverage gap, not just an unverified risk, since a live Office session with a multi-tool-calling model is needed to reproduce the original symptom.
